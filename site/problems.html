ModuleNotFoundError: No module named 'requests'

ModuleNotFoundError: No module named 'requests'

Symptom

Works in your terminal, fails under cron, systemd, sudo or CI; or fails right after creating a new venv.

Why it happens

  • A different interpreter runs the script than the one you installed into (system python3 instead of the venv)
  • The package was never installed in this environment
  • The import name differs from the package name (yaml is PyYAML)

Confirm

python3 -c 'import sys; print(sys.executable)'
python3 -m pip show requests
head -1 script.py   # which interpreter the shebang names

Fix

Run the script with the environment's own interpreter (/opt/app/.venv/bin/python script.py), or install the package into the interpreter that runs it with python -m pip install.

Prevent

One venv per application, a pinned requirements.txt, and absolute interpreter paths in crontabs and unit files.

ImportError: cannot import name 'x' from 'y'

ImportError: cannot import name 'Retry' from 'requests.packages.urllib3' (unknown location)

Symptom

An import that used to work fails after a dependency upgrade, or a module imports itself.

Why it happens

  • The name moved or was removed in a new major version
  • A local file shadows the library (a json.py or requests.py next to your script)
  • A circular import between two of your modules

Confirm

python3 -c 'import y; print(y.__file__, getattr(y, "__version__", "?"))'
ls *.py   # anything named like the library?
pip index versions y

Fix

Import from the library's current location, or pin the version your code was written for; rename local files that shadow libraries.

Prevent

Pin dependencies, read changelogs before major upgrades, and never name your files after modules.

error: externally-managed-environment

error: externally-managed-environment

× This environment is externally managed

Symptom

pip install (also with --user or sudo) is refused on a current Debian, Ubuntu or Fedora system.

Why it happens

  • The system Python's packages belong to the OS package manager (PEP 668)
  • pip would overwrite files apt or dnf installed

Confirm

ls /usr/lib/python3*/EXTERNALLY-MANAGED
python3 -m pip --version

Fix

Create a venv and use its pip and python: python3 -m venv .venv && .venv/bin/pip install -r requirements.txt. For command-line tools, pipx install <tool>. Use apt for OS-wide Python packages.

Prevent

Never install into the system Python; avoid --break-system-packages.

source: not found (activating a venv in cron or sh)

/bin/sh: 1: source: not found

Symptom

A crontab line or sh script that activates a virtual environment fails, or the venv is not used.

Why it happens

  • cron and many CI steps run /bin/sh (dash), which has no source
  • Activation only changes PATH for the current shell; it is never needed in automation

Confirm

ls -l /bin/sh
/opt/app/.venv/bin/python -c 'import sys; print(sys.prefix)'

Fix

Do not activate: call /opt/app/.venv/bin/python script.py directly. In sh, . (dot) is the POSIX spelling of source.

Prevent

Use absolute venv interpreter paths in crontabs, systemd units and CI steps.

Symptom

NoCredentialsError: Unable to locate credentials

botocore.exceptions.NoCredentialsError: Unable to locate credentials

Symptom

A boto3 script works on your laptop and fails in cron, a container, CI or on a new server, before any request is sent.

Why it happens

  • Nothing in the credential chain is set for this process: no AWS_* variables, no profile in ~/.aws, no SSO session, no role
  • cron, systemd and sudo run with another HOME or a clean environment, so ~/.aws and your exported variables are not there
  • A container on EC2 cannot reach the instance metadata service: IMDSv2 with a hop limit of 1 stops one network hop short of the container
  • The task or pod has no role attached (ECS task role, EKS IRSA or Pod Identity)

Confirm

Run automation with roles, not long-lived keys; test a new job with the same user and environment cron will use; make credential errors exit 2 with one clear line (awskit.run).

InvalidClientTokenId or SignatureDoesNotMatch

botocore.exceptions.ClientError: An error occurred (InvalidClientTokenId) when calling the GetCallerIdentity operation: The security token included in the request is invalid.

Symptom

  • InvalidClientTokenId: the access key was deleted or deactivated, belongs to another partition, or is a temporary (ASIA...) key used without its session token
  • SignatureDoesNotMatch: the secret key is wrong, or was copied with a space or a line break

Prevent

Prefer roles and SSO to static keys; when a key must exist, rotate it with a check (get-caller-identity) before deleting the old one.

Throttling: Rate exceeded (reached max retries)

botocore.exceptions.ClientError: An error occurred (Throttling) when calling the GetMetricStatistics operation (reached max retries: 4): Rate exceeded

Symptom

A script that calls AWS many times, often from a thread pool or several jobs at once, fails part-way. EC2 calls it RequestLimitExceeded, DynamoDB ProvisionedThroughputExceededException, S3 SlowDown.

Why it happens

  • Too many requests per second for the account, region and API: limits are shared by every job using them
  • The default (legacy) retry mode gives up after four retries
  • Many threads each retrying on their own make the burst worse

Confirm

grep -c 'reached max retries' job.log
CloudTrail: events with errorCode Throttling or RequestLimitExceeded at that time
aws service-quotas list-service-quotas --service-code ec2 --query 'Quotas[].QuotaName' | head

Fix

Create the client with Config(retries={"mode": "adaptive", "max_attempts": 10}): exponential backoff with jitter, and adaptive mode also slows the client down when throttled. Share one client between threads and keep the pool small.

Prevent

Retries configured on every client, fewer and bigger calls (paginators, filters, batch APIs), and jobs spread out in time instead of all at minute 0.
